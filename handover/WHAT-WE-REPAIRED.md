# Что уже отремонтировано

Первый доведённый до конца срез по [`docs/REPAIR-MAP.md`](../docs/REPAIR-MAP.md): чанк A
(контур приёмки) и чанк B (моб замечает игрока в креативе). Здесь только то, что можно
проверить командами из [`README.md`](README.md), и честная цена каждого шага.

## Как шли

Карта → протокол → **воспроизведение дефекта тестом** → поиск причины → минимальная правка →
двойная приёмка → запись в метрики. Ни один шаг не начинался со слов «кажется, дело в этом».

## Чанк B — цель в креативе

**Симптом:** призванный в креативе моб стоит и не атакует. Для того, кто тестирует в творческом
режиме, мод выглядит неработающим.

**Воспроизведение (RED):** тест `creative_player_is_targeted` падал с сообщением
`creative player must be targeted, target=null on tick 20` — то есть дефект зафиксирован
до правки, а не описан словами. Лог: `runtime/r1/evidence/b-red-02.log` (вне репозитория).

**Причина — три ванильных гейта 26.3, а не один:**

1. `Mob#asValidTarget` возвращал `null` для креативного игрока — цель отбрасывалась при установке;
2. `LivingEntity#canAttack` отвечал через `Player#canBeSeenAsEnemy`, а он ложен, пока выставлен
   `Abilities#invulnerable`;
3. `MeleeAttackGoal` для такой цели возвращал `canContinueToUse() == false` и в `stop()` обнулял
   цель — она мигала.

**Правка:** `src/main/java/dev/minemod/entity/ShellbackEntity.java`, +61/−1: два гейта открыты
только для креатива, добавлен приватный `ShellbackMeleeAttackGoal`, который продолжает
преследование и замах. Наблюдатель остаётся недоступной целью; урон по креативу не проходит —
это свойство режима, а не наша логика.

**Тест:** `src/gametest/java/dev/minemod/test/ShellbackCombatGameTest.java`, +25: один новый кейс.
Ни один существующий assert не ослаблен, константы поведения не менялись.

**Приёмка (прогнана координатором независимо от исполнителя):**

| Проверка | Результат |
|---|---|
| `clean build` | успех, 52 с |
| Серверные GameTests | **27/27** (26 модовых + ванильная заглушка), 5,019 с, 0 отказов |
| Отдельный `runClientGameTest` | успех, 65 с, exit 0 |
| Состав XML | проверен программно: 27 `testcase`, из них 26 с префиксом `minemod-test:` |

Запись приёмки: [`metrics/chunk-b.json`](../metrics/chunk-b.json). Коммит: `52e70fc`.

**Не проверено:** ручной шаг в клиенте (что моб визуально бежит и машет) и исключение
наблюдателя — оно доказано чтением кода, а не отдельным кейсом. Оба пункта записаны как
незакрытые, а не выданы за успех.

## Чанк C — ответная агрессия

**Симптом:** бьёшь в панцирь — удар отражается, а моб не отвечает и продолжает гулять.

**Воспроизведение (RED):** `retaliation_after_deflect` падал с `lastHurtByMob=null on tick 2` —
моб не знал, что его ударили.

**Причина:** `hurtServer` при отражении делает `return false` до `super.hurtServer`, поэтому
`LivingEntity` не запоминает обидчика; `HurtByTargetGoal` в селекторе цели отсутствовал вовсе.

**Правка:** `+11` в `ShellbackEntity.java` — `setLastHurtByMob` внутри `deflect` и
`HurtByTargetGoal` на приоритет 0. **Тест:** `+112`, только добавления; сценарий честный —
укрытие из двух блоков снимает линию видимости, моб берёт цель не «видя» игрока, а по памяти об ударе.

**Приёмка:** `clean build` 57 с, **28/28** (27 модовых + заглушка), клиентский прогон 62 с, exit 0.
Запись: [`metrics/chunk-c.json`](../metrics/chunk-c.json). Коммит: `b1db57c`.

**Не проверено:** ручной шаг в клиенте; изоляция assert'а о цели опирается на пройденную
предпосылку «линии видимости нет»; ответ на стрелу отдельным кейсом не покрыт — выведен из
ванильного предиката `HURT_BY_TARGETING`.

## Чанк D — гейт по типу урона

**Симптом:** крипер взрывается строго перед мобом — урон не проходит, «бессмертен спереди».

**Проверка гипотезы:** я предполагала по чтению кода, что настоящий взрыв приходит с `directEntity == null`
и поэтому уже проходит — то есть дефекта нет. Исполнитель это **опроверг**: в 26.3
`Explosion#getDefaultDamageSource` резолвит живой источник через `getIndirectSourceEntity`, и тот
возвращает самого крипера, поэтому взрыв приходил как `direct == causing == крипер` — по форме
неотличимый от удара. Это записано в `metrics/chunk-d.json` намеренно: гейт — эксперимент,
а не мнение координатора.

**Воспроизведение (RED):** взрыв спереди — `health 24.0 → 24.0`. После правки — `24.0 → 0.0`.

**Правка:** `+21/−1` — `canDeflect` принимает только ближние типы урона (`mob_attack`,
`mob_attack_no_aggro`, тег `is_player_attack`), поэтому удар волка, копья и булавы сохранён,
а взрыв, огонь, падение и магия проходят.

**Приёмка:** три чистые сборки подряд **29/29** (28 модовых + заглушка), клиентский прогон 53 с, exit 0.
Запись: [`metrics/chunk-d.json`](../metrics/chunk-d.json). Коммит: `dfa83df`.

**Найдено попутно:** тест чанка B проверял цель ровно на 20-м тике, а цель пересматривается через
случайный интервал в 10 тиков — за восемь прогонов он один раз упал. Ожидание увеличено до 40 тиков,
три прогона подряд зелёные. Флейк был в нашей приёмке, а не в продукте, и это тоже исправлено.

## Как повторить приёмку

```bash
cd <репозиторий>
git rev-parse HEAD                     # ревизия, к которой относится результат
export JAVA_HOME=<JDK 25>
export GRADLE_USER_HOME=<каталог вне checkout>
gradlew clean build                    # серверные GameTests входят в сборку
gradlew runClientGameTest               # отдельный клиентский прогон
```

Успех: XML `build/test-results/gameTest/game-test.xml` содержит 26 кейсов `minemod-test:` плюс
`minecraft:always_pass`, ноль `failure`/`error`/`skipped`; клиентский прогон завершается кодом 0.
Подробнее — [`docs/observability/ACCEPTANCE.md`](../docs/observability/ACCEPTANCE.md).

## Что дальше

Ремонтная серия остановлена по решению владельца на чанке D: для передачи этого достаточно.
Что осталось в карте и почему не делалось:

- **E (окно парирования)** — блокирован развилкой **F**: чем игрок закрывается до апгрейда щита.
  Это решение владельца, а не лаборатории.
- **G/H (визуал и иконки)**, **I** (рецепт в книге), **J/K** (спавн и биомы) — не начаты
  сознательно: они не входили в согласованный объём «первый срез + D».
